# Differenze tra disassembler lineare e interattivo
Il tool `objdump` di gcc è un disassemblatore lineare. Strumento molto semplice e facile da imparare. All'interno del corso l'architettura che analizzeremo non è RISC (reduced istruction set computer) quindi poche istruzione con formato fisso, ma CISC (complete istruction set computer) ovvero le istruzioni macchina non sono fisse ma spesso sono lunghe diversi byte. Ad esempio il byte 83 da solo è una ADD mentre 8B 83 è il codice operativo per una MOV. Un disassembler lineare quindi funziona bene con architettura RISC date le poche istruzioni di formato fisso. Un disassembler interattivo invece è un tool utile per architetture CISC. Il disassembler parte guardando nel file eseguibile una testata che viene chiamata entry point, l'indirizzo della prima istruzione da eseguire. Non è detto però che questo approccio funzioni sempre. Un disassembler lineare ad esempio in presenza di un JMP +5 non ha l'intelligenza necessaria per continuare a disassemblare dopo il JMP ma continua iterativamente. L'interattività del disassembler interattivo sta nel fargli capire le istruzioni che non riesce a decifrare e vedremo come farlo. Un disassembler interattivo invece è come lavorasse su i singoli blocchi del programma. Un disassembler lineare inoltre disassembla il segmento `.text` Prendiamo adesso il codice assembly di un eseguibile che utilizza uno switch.
![[switch_code.png|400]]
Dopo aver fatto alcune manipolazioni per lo stack e il prologo, tramite *argc* prende un valore che viene salvato in EAX, fa un confronto con il numero 50 in esadecimale, e dopo fa un JMP. Se EAX fosso inferiore a 50 allora si effettua un JMP all'indirizzo puntato dalla cella risultato della somma tra `0x804a008+4*EAX`. Attenzione alle parentesi quadre! Nel codice diasassemblato se vado a vedere l'indirizzo non trovo nulla, perché nella tabella non c'è codice ma contiene indirizzi. Questo meccanismo, per un disassembler lineare è molto difficile da smontare che per un disassembler interattivo.

# Ghidra
Ghidra è il disassembler interattivo sviluppato dal NSA che utilizzeremo nel corso. È il disassembler più evoluto in circolo. Permette di definire un progetto o di aprire progetti che possono essere non-shared o shared. Per aggiungere file da diasassemblare bisogna importare i file tramite il menu contestuale File oppure la scorciatoia `I`. Una volta scelto il file da importare Ghidra, presenta un riepilogo con il formato del file, il linguaggio dell'eseguibile con architettura di riferimento (x86 per noi), LE per little-endian, default o altro per la ABI e il compilatore con cui è stato compilato il file. Continuando Ghidra propone un rapporto con altre informazioni al suo interno come data di creazione, data di dell'ultima modifica, nomi di alcuni file sorgenti, ecc. I tool che offre Ghidra sono 4 ma noi essenzialmente utilizzeremo solo uno, il code browser. Come vedremo in futuro alcuni malware, possiedono meccanismi per capire se la macchina su cui si trovano ha installati debugger o disassembler quindi sarebbe ideale installer Ghidra sulla macchina host. Una volta aperto il file con Ghidra, appare un message box in cui viene chiesto se si vuole analizzare il file. Ovviamente la risposta è si e dopo ciò vengono presentati gli analizzatori che si possono applicare. Ogni motore non è controproducente verso altri ma al massimo si allunga di molto il tempo di disassemblaggio. Tutte le finestre di Ghidra sono sincronizzate tra di loro, quindi quando ci si muove nel codice in una, ci si muove anche nelle altre. Una finestra molto utile è la finestra che mostra le funzioni tramite il relativo tool che può essere selezionato per l'analisi. Non è scontato ma si possono trovare all'interno di questa finestra, il nome delle funzioni come definite dal programmatore oppure un default per indicare che è stata trovata una funzione. Un'altra finestra utile è il memory map che contiene tutte le regioni di memoria nello spazio lineare del processo. La finestra del function graph che rappresenta una funzione in blocchi. Per il programma che implementa uno switch, ogni caso è un blocco a se stante. Ghidra costruisce i riferimenti nel codice che facilitano molto il processo di reversing. Un'altra finestra è il function call graph che visualizza l'albero delle invocazioni delle funzioni. In Ghidra è molto importante andare a riconoscere le funzioni e questo avviene sia automaticamente, tramite le istruzioni CALL e RET sia con l'interazione con l'analista. Grazie all'interazione è possibile "dire" a Ghidra come del codice che non viene interpretato bene o affatto sia una funzione o un JMP o istruzioni per cammufare. Ultima ma non per importanza è la finestra listing, la finestra più utile che contiene il codice disassemblato.

## Applicazioni in Windows
In Windows ci sono due modi per scrivere applicazioni, le applicazioni console che sono senza GUI e le applicazioni con GUI. A differenza di Linux che nel kernel non ha librerie per aggiungere la parte grafica, che viene aggiunta tramite librerie esterne (vedasi KDE o GNOME per esempio), in Windows buona parte dell'interfaccia grafica è dentro al kernel e come si scrive un applicazione grafica è totalmente diverso che scrivere un applicazione senza GUI. Una semplice applicazione `W02.exe`, che apre una singola finestra bianca utilizza già molte cose del sistema operativo. Se disassembliamo `W02.exe` nella lista delle funzioni non troviamo il main, perché le applicazioni GUI in Windows non cominciano con una funzione main, ma con la funzione WinMain. Con Ghidra non riusciamo a trovare WinMain ma abbiamo però l'entry point che è molto utile per iniziare a cercare la funzione. Come riconoscere WinMain? Non c'è una strategia di base, ma sicuramente finché si sta inizializzando il processo o se sono alla chiusura del processo sono sulla strada sbagliata. Ghidra riconosce alcuni parametri per localizzare WinMain, ma se non riesce devo sapere come funziona WinMain guardando la documentazione. Nel caso di WinMain la documentazione riporta le seguenti informazioni: ![[winmain.png|400]]
In particolare `hIstance` è un handle d'istanza, in particolare per Windows un handle è un riferimento "opaco" ad un oggetto, cioè non permette di guardare al suo interno. Una volta trovato un candidato per WinMain gli assegno il prototipo su Ghidra andando a modificare il tipo di ritorno e i parametri di input. Dopo aver messo il prototipo Ghidra aiuta di più rispetto a prima. Il "trucco" per fare reversing di un `exe` è lavorare a saltelli, avanti e indietro. Si cerca la successiva API da invocare, si cerca di capire cosa fa ed il prototipo per facilitare il reversing. 

> [!important] Importante
> È molto importante fare sempre riferimento alla documentazione di Windows, anche se non è sempre esplicita.

Molti dati i programmi Windows li memorizzano come risorse, in apposite sezioni da cui vengono caricate. Un particolare tipo di risorse sono le risorse di sistema, che vengono riutilizzate spesso. Tutti gli identificatori che Windows usa, sono numeri definiti come MACRO, ma tali macro iniziano con delle lettere che sono proprie dell'API da utilizzare. Ghidra contiene un database con tali prefissi. Per avere il corrispettivo del ID per l'API bisogna utilizzare l'opzione `Set Equate` che mostra tutte le associazioni relative al numero.
Ricorda che sulla cima dello stack quando si invoca una funzione, c'è il primo parametro!
Le icone ed i cursori di un'applicazione GUI di Windows solitamente sono memorizzate all'interno di una struttura dati apposita, ovvero la `WNDCLASSEX`. Quindi più informazioni do a Ghidra più è facile fare reversing.
